# 0004. 업종 라벨 수집 방식과 알려진 한계

## 상태
승인됨 (2026-10-23)

## 배경
`sector.jsonl` 수집 과정에서 세 가지 문제를 차례로 발견하고 고쳤다.

### 1. 카테고리 하나가 --limit을 독식하는 문제
처음엔 카테고리를 순서대로 다 소진한 뒤 다음 카테고리로 넘어가는 구조였다.
앞쪽 카테고리 하나의 문서 수가 많으면(실제로 그랬음) 거기서만 --limit을
다 채워버려 21개 카테고리인데 라벨이 4개만 나왔다. → 카테고리별 큐를 만들고
한 바퀴씩 돌아가며 하나씩 뽑는 라운드로빈으로 교체.

### 2. 카테고리 트리 자체가 업종별이 아니었던 문제
처음 썼던 `분류:대한민국의 기업`의 하위 카테고리는 법적 형태(유한회사),
상장거래소(코스닥/코넥스), 소유형태(공기업/외국계), 특정 그룹(쌍용그룹) 등이
섞여 있어 "업종" 라벨로 쓸 수 없었다. → `분류:대한민국의 업종별 기업`으로
루트 카테고리 변경, 하위 25개가 실제로 건설/금융/IT/식품 같은 업종임을
라이브로 확인.

### 3. 카테고리별 문서 수가 너무 적은 경우
25개 중 일부(디자인 회사 1개, 건축 설계 사무소 2개, 오락 회사 2개, 폐기물
관리 회사 4개)는 train/val 분리조차 안 될 만큼 적었다. 디자인 회사는 더
구체적인 하위 카테고리(건축 설계 사무소)로 대부분 분산되어 있었고(이미
별도 라벨로 수집 중이라 데이터 손실은 아님), 나머지는 실제로 위키백과
문서 자체가 적은 경우였다. → `--min-category-size`(기본 10) 미만 카테고리는
라벨에서 제외.

## 알려진 한계 (고치지 않기로 함): 업종 중복 소속
위키백과 분류 체계는 트리가 아니라 그래프(DAG)라서, 회사 하나가 업종
카테고리 여러 개에 동시에 속할 수 있다 (예: 태양광 건설사가 "건설 기업"과
"태양 에너지 기업" 둘 다에 속함). 지금 구조는 **단일 라벨만 허용**하는데,
그런 회사가 어느 라벨로 수집되는지는 라운드로빈에서 어느 카테고리 차례가
먼저 왔는지에 달려있다 — 즉 사실상 임의 배정이다 (단, 같은 글이 두 라벨로
중복 저장되지는 않는다 — `seen` 집합으로 확인됨).

**고치지 않기로 결정**: 제대로 하려면 멀티라벨 분류(회사당 라벨 여러 개
허용, softmax 대신 sigmoid+BCE loss)로 바꿔야 하는데, 이번 프로젝트
규모에서는 비용 대비 효과가 낮다고 판단. 대신 이 한계를 명시적으로
기록해두고, 결과 해석·면접 설명 시 "일부 라벨은 중복 업종 중 하나로
임의 배정됐다"는 점을 밝힌다.
